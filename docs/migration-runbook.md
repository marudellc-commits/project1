# スカイベース神戸 サイトリニューアル 移行手順書

> 対象: skybase-shin-nagata.jp（株式会社マルカ / スカイベース神戸）
> 方針: **汚染歴のある2サイトは昇格させない。クリーンな新サーバー上でゼロから手動再構築する。**
> 環境: Xserver → 新Xserver（クリーン） / Diver → RE:DIVER / Classic → ブロックエディタ

## 0. 前提と環境整理

### 環境の呼び方（この手順書での定義）

| 呼称 | 内容 | 役割 | 汚染 |
|---|---|---|---|
| **旧本番** | skybase-shin-nagata.jp（Diver・Classic） | ブログ・LPの **元コンテンツ抽出元**（WXR/HTMLのみ） | 汚染歴あり |
| **参照ステージング** | skybase.marudellc.com（RE:DIVER・ブロック） | **デザインの見本**。見ながら手動再構築、エディタ上のコピペ元 | 汚染歴あり |
| **新クリーンサーバー** | 新規Xserver（クリーン） | **ここでゼロから新規構築 → 新本番にする** | クリーン |

**要点: 「移行」ではなく「再構築」。** 汚染歴のある2サイトからは DB・ファイル・テーマ・プラグインを **一切持ち込まない**。新クリーンサーバーへ持ち込むのは次の3種類だけ:
- (a) **スキャン済みメディア**（画像・PDF等）
- (b) **スキャン済みWXR**（ブログ本文のテキストデータ）
- (c) **エディタ上でコピペするブロック/HTML**（貼付後に再スキャン）

### 全体フロー（ご指定の4ステップに対応）

1. **サーバー変更**（独自メール設定もこの時に実施）… Phase 1
2. **新サーバーでWordPress新規**… Phase 2
3. **スキャン済みメディアのアップロード**… Phase 3
4. **skybase.marudellc.com を見ながら新規構築（コピペ可能部分はコピペ）**… Phase 4〜7

- ✅ ブログ・LPの元データは **旧本番（skybase-shin-nagata.jp）** から抽出
- ✅ DNS/ネームサーバーは **Xserver** で管理
- ✅ 独自メールは **旧サーバー** にホスト ← **今回の最大の注意点**。Phase 1・9で重点対応
- 前提: フォームは **Contact Form 7**

### 確定事項（切り替え方式）

- ✅ ドメインは **XServer Domain（エックスドメイン）** 管理・アカウント **合同会社MARUDE（chg10087）** → **ドメイン移管（譲渡）は不要**（自社管理・XServer Domain内で完結）。利用期限 2027-05-31・有効
- ✅ **現在の適用先: XServer Business**（NS: ns1〜3.xbiz.ne.jp）で稼働中
- ✅ **新サーバー: 通常のエックスサーバー**（安価・十分な性能）→ 切り替えは **XServer Domainで「ドメイン適用先サービス」を Business → XServer に変更**（NSが ns*.xserver.jp に変わる）。書類不要

## 1. 事故防止の原則（最重要）

**原則1: 汚染2サイトから実行物を持ち込まない**
DB丸ごと・wp-content丸ごと・テーマ・プラグインのコピーは **すべて禁止**。バックドアはDBの`wp_options`/`wp_users`、テーマ/プラグインのPHP、uploads内の隠しPHPに潜む。ここを断ち切るのが「クリーンサーバーで再構築」の目的。

**原則2: コピペにも汚染は乗りうる**
marudellcや旧本番から **レンダリング後HTMLをコピペする際、注入スクリプト（外部ドメインを読む`<script>`、不審な`<iframe>`、隠しリンク）が紛れる**ことがある。貼付後は必ずスキャン（手順は付録B）。エディタ上のブロックコピペも同様。

**原則3: 公開前は必ず noindex、公開時に必ず noindex 解除**
ステージング期間中の誤インデックスと、公開後の解除忘れ（＝検索圏外に落ちる）が両方致命的。切り替えチェックリストの筆頭に置く。

**原則4: 破壊的操作の前に必ずバックアップとdry-run**
DNS切り替え・URL一括置換・旧サーバー削除の前に、必ず取り返しがつく状態を作る。`search-replace`は必ず`--dry-run`から。

## Phase 3: スキャン済みメディアのアップロード【ご指定③】

uploadsは「画像・PDF等だけ」が正常。PHP等が混ざっていたら感染物です。

- [ ] SSHで、画像・文書系拡張子**だけ**を旧本番から取得（実行ファイルは持ち込まない）
  ```bash
  rsync -avz \
    --include='*/' \
    --include='*.jpg' --include='*.jpeg' --include='*.png' --include='*.gif' \
    --include='*.webp' --include='*.pdf' --include='*.mp4' --include='*.mp3' \
    --include='*.woff' --include='*.woff2' --include='*.ico' \
    --exclude='*' \
    旧本番:/path/wp-content/uploads/ ./uploads_clean/
  ```
  ※ `.svg` はスクリプトを埋め込めるため**あえて除外**。必要なSVGは中身を目視確認して個別に。
- [ ] アップロード前に実行ファイルが紛れていないか検査（**1件でも出たら感染物として除去・原因調査**）
  ```bash
  find ./uploads_clean -type f \
    \( -iname '*.php' -o -iname '*.phtml' -o -iname '*.php[0-9]' \
       -o -iname '*.pht' -o -iname '*.phar' -o -name '.htaccess' \) -print
  ```
- [ ] 不審コード走査
  ```bash
  grep -rniE 'eval\(|base64_decode|gzinflate|shell_exec|system\(' ./uploads_clean | head
  ```

- [ ] 問題なければ新サーバーの `wp-content/uploads/` へアップロード

## Phase 9: 本番切り替え（DNS → 新クリーンサーバー）

> ⚠️ Xserver間の切り替えは、ドメイン設定の付け替え中に **数時間〜最大24時間、Webとメールが不通**になりうる。低トラフィックの時間帯にメンテナンス枠を取り、クライアントへ事前告知する。hostsファイルで新サーバーを**事前に完全確認**してから実施すれば、不通枠を最小化できる。

### 9-0. 切り替え方式（XServer Business → 通常エックスサーバー）

現構成: ドメインは XServer Domain 管理・現適用先は XServer Business（NS: `ns1〜3.xbiz.ne.jp`）。新サーバーは通常のエックスサーバー。

- **推奨（クリーンで確実）**: 新Xserverにドメイン設定を追加 → hostsで表示・フォーム・メールを完全確認 → **XServer Domainの「ドメイン適用先サービス」を Business → XServer に変更**（NSが `ns*.xserver.jp` に切り替わる）。**ドメイン移管の書類は不要。** NS変更の反映に **数時間〜最大72時間**（多くは24h以内）。反映中は名前解決によって旧Business/新Xserverのどちらかに振れる。
- **低ダウンタイム代替（任意・上級）**: NSはBusinessのまま、**Business側のDNSレコード設定でA/MXを新XserverのIP・メールホストに向ける**。事前にレコードのTTLを下げておけば切り替えが速く、NS委譲の伝播待ちを避けられる。※Business契約を稼働させたまま運用する必要あり。
- **注意（共通）**: いずれの方式でも **web と mail は一体で新サーバーへ移る**（適用先＝A/MXが一括で切り替わる）。**mailを新サーバーで受けられる状態（アカウント再作成済み）にしてから**切り替えること。
- SSLは新Xserverで**無料独自SSLを新規発行**（Business↔Xserverはサービスが別なので証明書は引き継がない。無料なので実務上問題なし）。
- どちらも、hostsファイルで新サーバーの表示・フォーム・メールを事前確認済みであること（Phase 1）。

### 9-1. 受け入れ準備

- [ ] 新サーバーにドメイン設定済み・**SSL発行手順を最終確認**
- [ ] **全メールアカウントが新サーバーに再作成済み＋過去メール移行済み**（Phase 1）

### 9-2. URL最終置換（仮URLで構築した場合のみ）

- [ ] hosts方式で最初から本ドメイン構築していれば**不要**
- [ ] 仮サブドメイン等で構築した場合のみ、`search-replace`で本ドメインへ（**dry-runから／guid除外**）
  ```bash
  wp search-replace '仮URL' 'https://skybase-shin-nagata.jp' \
    --all-tables-with-prefix --skip-columns=guid --dry-run
  ```

### 9-3. 切り替え本番作業（順序が重要）

1. [ ] 新サーバーの直前フルバックアップ取得
2. [ ] **noindex を解除**（表示設定の「検索避け」を外す）★最頻出の事故ポイント
3. [ ] Basic認証を解除
4. [ ] 9-0の方式で**ドメイン/DNSを新サーバーへ切り替え**（ネームサーバー適用先 or Aレコード＋MX）
5. [ ] `robots.txt` が本番用（クロール許可）か確認
6. [ ] **切り替え後〜最大72時間は、新旧両方のメールボックスを確認**（浸透中は旧サーバーにも着信しうる。取りこぼし防止）
7. [ ] 複数回線で新本番の表示・**https**・メール送受信を確認

### 9-4. リダイレクト（スラッグ不変なので原則不要）

- [ ] 大量301は不要。**正規化のみ**（http→https / www有無 / index.php有無）を`.htaccess`で統一
- [ ] 統廃合で消したLP/フォームURLがあれば、そのURLだけ関連ページへ301

## 付録B: よく使うコマンド

```bash
# URL置換（必ずdry-runから／guidは触らない）

```
